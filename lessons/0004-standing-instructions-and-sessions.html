Standing instructions and sessions

Lesson 1 said context is a budget. Lesson 3 closed the loop within one task. Now the long game: what you load into every session, and how you keep sessions from decaying.

1. Everything you pre-load is spent every time

Claude Code reads CLAUDE.md at the start of every conversation, so every line competes for the same attention budget as your actual task. The official guide gives one test per line: would removing this cause Claude to make mistakes? If not, cut it. Its warning is blunt: bloated files cause Claude to ignore your real instructions.

Keep: commands Claude can’t guess, style rules that differ from defaults, test runners, branch and PR etiquette, project-specific architecture decisions, environment quirks, non-obvious gotchas.
Cut: anything derivable from reading the code, standard conventions, long API docs (link instead), fast-changing facts, file-by-file tours, “write clean code”.

This echoes the ETH Zurich finding from lesson 1: LLM-generated context files raised cost without improving success. The guide suggests /init as a starter to refine, so treat its output as a draft to prune, not a finished file. If Claude skips one rule, emphasize that single line. Emphasize many and none stands out.

2. Advice, knowledge, isolation, or guarantee?

Not everything belongs in CLAUDE.md. The guide separates the tools by how reliably they act and when they cost context:

flowchart TB
  S["A new rule or piece of context"] --> A{"Must happen every time, no exceptions?"}
  A -->|Yes| H["Hook: deterministic, not advice"]
  A -->|No| B{"Needed in most sessions and not guessable?"}
  B -->|Yes| C["CLAUDE.md: short and pruned"]
  B -->|No| D{"Needed only sometimes?"}
  D -->|"Knowledge or workflow"| K["Skill: loaded on demand"]
  D -->|"Reads lots of files"| U["Subagent: separate context"]

The key distinction: CLAUDE.md instructions are advisory, while hooks are deterministic and guarantee the action happens (for example, run the linter after every edit, or block writes to a migrations folder). The guide’s fix for a bloated CLAUDE.md is to delete what Claude already does right, or convert it to a hook. Connect this to lesson 3: a Stop hook is how a verification check becomes a hard gate.

3. Session hygiene

/clear between unrelated tasks. Mixed-topic “kitchen sink” sessions fill the window with irrelevant history.
Two failed corrections, then clear. If you’ve corrected the same issue more than twice, the context is cluttered with failed approaches. Restart with a sharper prompt that includes what you learned.
/compact <focus> or rewind and summarize when history is valuable but long. You can tell it what to preserve.
Subagents for investigation. Research reads many files; a subagent does that in its own window and returns a summary. Scope exploration either way, or “investigate X” can read hundreds of files.
/btw for side questions whose answers shouldn’t stay in context. Name long-running sessions so you can resume them like branches.

The guide also says these are starting points: sometimes you should let context accumulate because you’re deep in one hard problem and the history is the asset. Judgement still applies.

The human side: shorter, cleaner sessions also produce output you can actually review (lesson 2). A spec written to SPEC.md and executed in a fresh session gives you a document to review against, instead of a long transcript to remember.

4. Your turn

Three small actions this week: (1) run /context to see what your sessions load, then prune your CLAUDE.md with the one-line test; (2) pick one rule Claude should follow every time and move it into a hook; (3) the next time you correct Claude twice on the same thing, /clear and rewrite the prompt instead of arguing.
