Closing the loop: verification you can trust

You told me your habit with Claude Code: run it, see it roughly works, accept. This lesson is about replacing “roughly works” with something stronger, without turning you into a full-time reviewer.

1. Why “it looks done” isn’t enough

The Claude Code best-practices guide puts it plainly: Claude stops when the work looks done. If it has no check it can run, “looks done” is its only signal, and you become the verification loop, so every mistake waits for you to notice it. The guide lists this as a named failure, the trust-then-verify gap, with the fix: always provide verification, and if you can’t verify it, don’t ship it.

Connect it to lesson 2: debugging and code reading were where the skill gap showed up. A superficial check leans on exactly the skills that are weakest when you delegate everything. Better automated checks protect you from that.

2. Three layers of verification

flowchart LR
  A["Spec or plan: files, out of scope, end-to-end check"] --> B["Agent implements"]
  B --> C["Self-check: tests, build, curl, screenshot"]
  C -->|fail| B
  C -->|pass, with evidence| D["Fresh-context review of the diff"]
  D --> E["You: read the evidence and diff, run it once"]
  E --> F["Commit"]
Layer 1, the agent checks itself. Give it something that returns pass or fail: tests, a build exit code, a linter, a screenshot to compare. Willison adds that passing tests don’t prove the code works as intended, so also have the agent exercise it for real (curl for APIs, browser automation such as Playwright for UIs) and fold any bugs it finds back into permanent tests.
Layer 2, evidence, not assertions. Ask it to show the command it ran and what came back. Claude Code’s guide notes that reviewing evidence is faster than re-running verification yourself. Willison’s Showboat tool records commands together with their real output to discourage an agent from writing what it hoped happened.
Layer 3, fresh eyes. A reviewer in a new context (a subagent or second session) sees only the diff and your criteria, not the reasoning that produced it. Caveat from the same guide: a reviewer asked for gaps will usually report some, so tell it to flag only correctness or stated-requirement gaps, or you’ll chase over-engineering.

The guide also lets you choose how hard a check gates the work: in one prompt, across a session with a goal condition, or as a deterministic Stop hook that blocks finishing until the check passes. Start with the prompt version.

3. Keep the unit of work small enough to review

Your attention is the scarce resource from lesson 2, so shrink what lands in front of it. The guide’s flow is explore, plan, implement, commit, using plan mode for the first two. Its own rule of thumb: if you could describe the diff in one sentence, skip the plan. For larger features, have Claude interview you, write a SPEC.md, then start a fresh session to implement it. The best specs name the files and interfaces involved, state what’s out of scope, and end with an end-to-end verification step.

Honest gap: I found no solid research on how big a diff a person can review well, so I won’t invent a number. Use the one-sentence test and your own experience of when you start skimming.

4. Your turn

Next feature you give Claude Code, add two lines to the prompt: “Write a failing test first, then make it pass, and exercise the result the way a user would. Show me the commands and output.” Then read the diff for one function you wouldn’t have known how to write, and ask Claude to explain it. That last step is the lesson-2 habit (comprehension after generation).
